# Normalized Quantity Column — Design

**Date:** 2026-07-27
**Status:** Approved, ready for implementation planning
**Builds on:** `2026-07-27-sorting-filtering-improvements-design.md`

## Problem

Ethereum has no fractional integers. A token contract that wants to represent fractional
amounts declares a `decimals` value, and every on-chain quantity is stored as an integer
scaled by `10^decimals`. The dataset stores those raw scaled integers, so the Quantity
column shows `80,000,000` for what a user transferred as **80 USDT** — USDT declares
`decimals: 6`.

The table currently has no way to express the human-facing amount. This design adds a
**Normalized Quantity** column, immediately to the right of Quantity on the Token
Transfers tab, showing `quantity ÷ 10^decimals` with the token symbol.

## Data source and its measured limits

`tokens.csv` (39 MB, 223,930 rows, 223,924 distinct contracts) is an export of BigQuery's
token-contract table, carrying `address, symbol, name, decimals, total_supply,
block_timestamp, block_number, block_hash`.

Coverage was measured with an RFC4180 parser against the 43,941 transfer rows in
`public/data/rows.csv.gz`:

| Measure | Value |
|---|---|
| Distinct token contracts in the dataset | 955 |
| Of those, present in `tokens.csv` | 66 |
| Of those, carrying a usable non-empty `decimals` | **64** |
| Transfer rows that can be normalized | **20,352 / 43,941 = 46.3%** |

**The gap is not random.** USDC (`0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48`) is absent
from `tokens.csv` and is by itself 10,942 rows — 25% of every transfer in the dataset. DAI
(`0x6b175474e89094c44da98b954eedeac495271d0f`, 336 rows) is absent too. USDT and WETH are
present. `tokens.csv` spans blocks 824,235–25,610,905, so this is not a date cutoff — the
source table simply has no row for those contracts.

Two parsing hazards were confirmed and must be respected by any code reading either file:

- **`tokens.csv` needs a real CSV parser.** Token `name` values contain commas and quotes;
  naive comma splitting silently corrupts every field after `name`.
- **`rows.csv.gz` needs one too.** `event_signature` values such as
  `Transfer(address,address,uint256)` are quoted and contain commas.

Row-kind breakdown of the 43,941 transfers: 43,595 ERC-20, 292 ERC-721, 54 ERC-1155.
Decimals are meaningful only for ERC-20 — for NFTs `quantity` is a token *count*, not a
divisible amount, and `tokens.csv` leaves their `decimals` empty regardless.

## Decisions

| # | Decision | Rejected alternatives |
|---|---|---|
| 1 | Rows with no known decimals render **`—`**, never a guessed divisor | Default to 18 (the ERC-20 convention) — would misreport every USDC row by a factor of 10^12, rendering an 80 USDC transfer as `0.00000008` |
| 2 | Decimals ship as a **small prep-time lookup artifact**; the normalized value is derived at render | Bake a `normalized_quantity` column into `rows.csv.gz` (puts a derived value inside the artifact the All Records tab presents as raw stored values, and forces a re-prep of the 2.19 GB source); load `tokens.csv` in the browser (39 MB to use 64 rows) |
| 3 | The column is **sortable and range-filterable**, exactly like every other column | Display-only (would be the sole non-sortable column, reading as an oversight); sort-only |
| 4 | The cell shows **value + symbol** (`80 USDT`) | Value only — the scale differs per row, so a bare number is ambiguous without cross-referencing the Token Contract column |
| 5 | Display truncates to **6 fraction digits with thousands separators**, and marks dust as `<0.000001` | Match `weiToEth` exactly (no separators, dust truncating to a bare `0` — indistinguishable from a real zero); full precision (18-digit tails destroy scannability) |
| 6 | The lookup is generated by a **standalone script**, not folded into `data:prep` | Fold into `prepare-dataset.mjs` — would require the gitignored 2.19 GB source every time the token data is refreshed |

## 1. Build-time artifact

New script `scripts/prepare-tokens.mjs`, wired as `npm run data:tokens`:

```
node scripts/prepare-tokens.mjs <tokens.csv> [--rows public/data/rows.csv.gz] [--out public/data]
```

1. Stream `rows.csv.gz`, collecting the distinct non-empty `address` values (955).
2. Stream `tokens.csv`, keeping only rows whose `address` is in that set **and** whose
   `decimals` parses as an integer in `0..77`.
3. Write `public/data/tokens.json`.

```json
{
  "contractsInDataset": 955,
  "contractsWithDecimals": 64,
  "tokens": {
    "0xdac17f958d2ee523a2206206994597c13d831ec7": { "symbol": "USDT", "decimals": 6 }
  }
}
```

Roughly a few KB. The two coverage counts live in the artifact so the UI can state its own
limitation instead of hard-coding a number that would rot the moment a wider export lands.

Addresses are lowercased on both sides before matching. `tokens.csv` contains 6 duplicate
rows across 223,924 distinct addresses — all 7 rows of a single contract (`yLink`,
`0xff0cca…1437`, not one of the dataset's 955), and **all agreeing on `decimals: 18`**.
No address in the file disagrees with itself, so last-row-wins is both sufficient and
deterministic.

Keeping this separate from `data:prep` is the point of decision 6: refreshing token
metadata is a seconds-long job over a 39 MB file, not a re-run over the 2.19 GB export.

## 2. Runtime registry

New module `src/data/tokenRegistry.ts`:

```ts
export interface TokenInfo { symbol: string | null; decimals: number }
export type TokenRegistry = Map<string, TokenInfo>   // key: lowercased address

export function parseTokenRegistry(json: unknown): TokenRegistry   // pure, total
export function tokenRegistryProvider(url?: string): { load(): Promise<TokenRegistry> }
```

`parseTokenRegistry` is total: any shape it doesn't recognise yields an empty registry, and
individual malformed entries are skipped rather than aborting the parse.

`App.tsx` loads it alongside the rows. **A registry failure never fails the dataset load** —
a 404, a network error, or a malformed payload resolves to an empty registry, and the app
behaves exactly as it does today with the new column showing dashes in every row. No error
banner: the dashes plus the dictionary entry already communicate the state, and a banner
would imply something is broken when the app is working as designed.

## 3. Math

Added to `src/data/transform.ts`, alongside the existing `BigInt`-only helpers:

```ts
export function normalizeQuantity(quantity: string | null, decimals: number): string | null
export function formatNormalizedQuantity(quantity: string | null, decimals: number): string | null
export function compareNormalizedQuantity(
  aQty: string | null, aDec: number | null,
  bQty: string | null, bDec: number | null,
): number
```

- **`normalizeQuantity`** — exact, full-precision decimal string. `BigInt` only, never
  `Number`, for the same reason the rest of the module is: these values reach 256 bits.
- **`formatNormalizedQuantity`** — display form. Thousands separators on the integer part
  (matching `BigNumCell`, the Quantity column it sits beside), fractional part truncated to
  6 digits with trailing zeros stripped. A **non-zero** value that truncates to zero renders
  `<0.000001`, so dust is never mistaken for nothing. A true zero renders `0`, faint, the
  same treatment `EthValueCell` gives it.
- **`compareNormalizedQuantity`** — compares `a / 10^da` against `b / 10^db` by
  cross-multiplication (`a·10^db` vs `b·10^da`), exact across differing scales, so 0.5 WETH
  and 80 USDT order correctly. Null quantity or unknown decimals sorts last, matching
  `compareNumericStrings`.

Decimals that are non-integer, negative, or above 77 are treated as unknown.

## 4. Column wiring

In `columns.tsx`, appended immediately after `quantity` in the transfers tab:

```ts
helper.accessor((r) => r.quantity, {
  id: 'normalized_quantity',
  sortDescFirst: true,
  // sortingFn / filterFn are closures over the registry — see below
})
```

The accessor returns raw `quantity`; the sort and filter functions read `row.original` for
both `quantity` and `address`. Because these functions close over the registry rather than
being shared by string key, they are passed **by reference** — no `SortingFns` / `FilterFns`
module augmentation is needed, unlike `bignum` and `rangeEth`.

`sortDescFirst: true` follows the existing intent behind `DESC_FIRST_FIELDS`: this is a
magnitude, like the `quantity` column it mirrors. It is not added to that set, which is keyed
by `DictionaryField` and drives the raw columns.

**The range filter's bounds are typed in token units.** For each row the bound is scaled by
that row's own `10^decimals` via the existing `decimalToWei`, then compared against the raw
`quantity` with the existing `rangeFilter` — so `≥ 1` means one whole token regardless of
which token the row is. Rows with unknown decimals fail a set bound, consistent with how
`rangeFilter` already treats an unparseable value. The Min/Max inputs are labelled
`(token units)`, since unlike the ETH and Gwei columns the unit genuinely varies per row.

`getColumnsForTab(tab, registry)` becomes a function of the registry, so `DataTable`
memoizes the result on `[tab, registry]`. The comment at `DataTable.tsx:49` asserting that
the function returns module-level constant arrays becomes false and is updated in the same
change.

**Transfers tab only.** The All Records tab keeps showing raw stored values — a derived
column there would contradict that tab's stated contract.

## 5. Dictionary

`dictionary.ts` gains a `normalized_quantity` entry with `source: 'derived'` and a new
`availability: 'derived'`. The new availability value is what keeps it out of
`LOADED_COLUMNS`, which is typed `field: keyof EthRecord` and drives global search, column
stats, and the all-columns export — none of which can read a field that does not exist on a
record.

`DictionaryField` widens to `keyof EthRecord | 'input_tx' | 'normalized_quantity'`.

`DictionaryPanel` already renders stats only for `availability === 'loaded'`, so the new
entry needs no stats handling; it gains a `'derived'` branch beside the existing
`'on-demand'` one, reading **Computed in the browser**.

The entry's description states the limitation plainly — that the value is derived from a
token-decimals lookup, and that contracts absent from it show no value.

## 6. Export

`buildCsv` gains an optional resolver for derived columns, so a visible column whose id is
not a `keyof EthRecord` still exports a value instead of silently emitting an empty string.

**Visible columns** exports `normalized_quantity` as the exact, full-precision value —
no thousands separators, no symbol — so the CSV re-imports cleanly. Display truncation is a
display concern and must not reach the file, consistent with the project's lossless-decimal
rule.

**All 34 columns** is unchanged: the derived column is not a loaded column, so the menu
label stays accurate.

## 7. Error handling

| Condition | Behavior |
|---|---|
| `tokens.json` missing, 404, or malformed | Empty registry; column renders `—` throughout; app otherwise unaffected; no error banner |
| Contract absent from registry | `—` |
| `decimals` non-integer, negative, or > 77 | Treated as unknown → `—` |
| `quantity` null (transaction rows) | `NullCell`, same as the Quantity column |
| ERC-721 / ERC-1155 rows | `—`, which is correct: those quantities are counts, not divisible amounts |
| Non-zero value below display precision | `<0.000001` |
| True zero | Faint `0` |

## 8. Testing

TDD, matching the repo's existing per-module suites.

- **`transform.test.ts`** — 6-digit truncation; trailing-zero stripping; the `<0.000001`
  dust case; true zero; `decimals: 0`; thousands separators on large values; null quantity;
  the USDT worked example (`80000000` @ 6 → `80`).
- **`tokenRegistry.test.ts`** (new) — valid parse; unknown shape → empty; individual
  malformed entries skipped; address lowercasing; provider 404 → empty registry.
- **Sort** — cross-scale ordering (0.5 WETH vs 80 USDT); unknown-decimals rows last; ties.
- **Filter** — a bound scales per row's own decimals; unknown-decimals rows excluded when a
  bound is set; no bound passes everything.
- **`DataTable`** — the column renders immediately right of Quantity on the transfers tab,
  is absent from the transactions and All Records tabs, shows `symbol` beside the value, and
  shows `—` for an unregistered contract.
- **`exportCsv.test.ts`** — the derived column exports the exact full-precision value with
  no separators and no symbol; the all-columns export is unchanged.
- **`scripts/prepareTokens.test.mjs`** (new) — filters to dataset contracts; skips empty and
  out-of-range decimals; parses quoted names containing commas; emits correct coverage counts.

## Expected result

20,352 of 43,941 transfer rows (46.3%) show a normalized value; the remainder show `—`.
A raw quantity of `80,000,000` on a USDT row renders as `80 USDT`.

## Out of scope

- **Widening coverage.** The 53.7% of rows without decimals — USDC above all — is a data
  limitation, not a code one. Fixing it means a wider export from the BigQuery token table
  filtered to the 955 contracts in this dataset. Because the lookup is a standalone artifact
  (decision 6), that refresh regenerates `tokens.json` in seconds with **no application code
  change**.
- **A hard-coded fallback table** of well-known token decimals. It would fix USDC and DAI at
  the cost of an unversioned, ad-hoc source of truth sitting next to a real one.
- **Showing the symbol on the Token Contract column**, or a token-level stats tile. Both are
  plausible follow-ons from having a registry loaded; neither is part of this request.
- **USD or fiat valuation.** Requires price data the dataset does not contain.
